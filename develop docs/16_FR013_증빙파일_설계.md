# FR-013 자산 증빙파일 설계

## Goal framing

- 사용자: 직원, 담당자, 관리자
- 문제: 현장사진·영수증·검수서·폐기증빙이 자산 이력과 분리되면 승인과 감사 근거가 누락된다.
- 변화: 자산 상세에서 증빙을 조직·권한 범위 안에서 조회하고 담당자가 추가·비활성화한다.
- 성공: 위장·초과·권한 우회를 차단하고 업로드·다운로드·비활성화가 모두 감사된다.
- 제외: 외부 오브젝트 저장소, 악성코드 검사, 운영 물리 삭제.

## 요구사항 계약

| 항목 | 계약 |
|---|---|
| 사전조건 | 활성 세션, 동일 조직 자산, 담당자 이상은 변경 권한 보유 |
| 입력 | 자산 ID, PHOTO/RECEIPT/INSPECTION/DISPOSAL, 원본명, JPEG/PNG/PDF binary |
| 처리 | MIME·매직바이트·1~5 MiB 검증 → 무작위 키·SHA-256 → 저장 → 짧은 DB 트랜잭션 |
| 출력 | 파일 ID·표시명·MIME·크기·체크섬·상태 또는 안전한 오류 |
| 실패 | 위장 400, 권한 403, 없음 404, 초과 413, 미지원 415 |
| 데이터 | file_records + asset_files + audit_logs; 비활성 시 원본·관계 보존 |
| 인수기준 | 목록/다운로드, 역할 역조건, 감사 3종, Docker 영속성, desktop/mobile 화면 통과 |

## 데이터 흐름

`Browser → /api/enterprise/assets/:id/files → Controller → File Service → LocalFileStore + File Repository → PostgreSQL → Repository → Service → Controller → JSON/Download → Browser`

바이너리를 먼저 제어된 저장소에 `wx`로 기록한다. 이후 파일 메타데이터·자산 관계·업로드 감사를 하나의 짧은 DB 트랜잭션으로 커밋한다. DB가 실패하면 이번 요청에서 새로 만든 무작위 키 파일만 경계 검증 후 정리한다. 다운로드는 활성·조직 범위 확인 후 감사하고 전송한다. 비활성화는 DB 상태와 감사를 원자적으로 변경하며 물리 파일은 보존한다.

## 저장·DB 정책

- 키: `{organizationId}/{yyyy}/{mm}/{40hex}.{ext}`
- 원본명: 표시·다운로드 전용, 경로에 미사용, 제어문자 제거·255자 제한
- 무결성: SHA-256, MIME·magic signature 동시 확인
- PostgreSQL: status/storage_driver/file_type/size CHECK, deactivated_by FK, FK 인덱스, 조직별 ACTIVE 부분 인덱스
- Docker: 기존 3서비스 유지, backend에 `file-data` named volume만 추가
- 운영: production은 외부 저장 드라이버가 없으면 설정 단계에서 중단한다.

## 화면 상태

정상 목록, 빈 상태, 파일 선택 검증, 업로드 중 버튼 비활성, 성공 후 재조회, API 오류 메시지, 모바일 단일 열을 제공한다. 파란 사이드바에는 공식 반전 로고를 사용한다. HTML mock과 컨셉에는 생성 메타데이터를 표시하지 않는다.

## 테스트

- 단위: signature, MIME, 크기, 유형, 원본명, 무작위 키, 경로 탈출, CSRF 헤더
- 통합: USER 403, 위장 400, 미지원 415, 초과 413, 정상 업로드·목록·다운로드·감사·비활성·404·DB 보존
- E2E: 자산 상세 증빙 섹션, 허용 형식 안내, desktop/mobile 수평 넘침, 공식 로고, 콘솔
- 운영: 3 health, migration/index, volume 쓰기, 로그, backup/restore, dependency/Secret/diff
