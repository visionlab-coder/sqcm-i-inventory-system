# FR-025 구매 요청 설계·개발 체크리스트

## Goal Framing

- 사용자: 구매가 필요한 직원과 요청 검토 담당자
- 현재 문제: `PURCHASE` 요청에 제목·사유만 있어 구매 판단에 필요한 필수정보가 누락될 수 있다.
- 변화: 품목·수량·금액·비용센터·필요일·사유가 검증된 하나의 요청으로 저장된다.
- 성공 지표: 필수정보 누락 저장 0건, 잘못된 수량·금액·날짜 400 거부, 정상 요청 조회 가능.
- 제외: 발주·입고·검수·자산 자동 생성과 외부 연동.

## Specification

| 조건 | 완료 기준 |
|---|---|
| 정상 | itemName 2~150자, quantity 1~100,000, estimatedAmount 0 초과·소수 2자리, costCenter 2~50자 코드, neededAt 실제 YYYY-MM-DD, reason 2자 이상 |
| 실패 | 필수값 누락·범위 초과·잘못된 날짜를 400 `VALIDATION_ERROR`와 해당 `fieldErrors`로 거부 |
| 권한 | 로그인 USER 이상 생성 가능, 다른 조직 ID는 403 |
| 데이터 | 정규화된 payload를 매개변수 JSONB로 저장하고 요청 생성 감사 로그 기록 |
| 화면 | 요청함에 모든 필수 label·HTML 제약·저장 오류 메시지·구매정보 요약 표시 |
| 테스트 | 정상·누락·수량·금액·날짜·조직 권한 단위/HTTP 검증 |

## 데이터 왕복

구매 폼 → Nginx `/api` → 세션·CSRF → Router → `createRequest` → `normalizePurchasePayload` → 매개변수 JSONB INSERT → 감사 로그 → JSON 응답 → 요청함 재조회·구매 요약 표시.

## DB 결정

- 기존 `workflow_requests.payload JSONB NOT NULL`은 요청 유형별 확장 필드 저장 목적으로 유지한다.
- 금액은 JavaScript 계산 손실을 막기 위해 소수 둘째 자리 문자열로 정규화한다. 발주 생성 시 PostgreSQL `NUMERIC(15,2)` 경계에서 다시 검증한다.
- 이번 단일 기능은 스키마를 바꾸지 않으므로 기존 migration checksum과 복구 기준을 유지한다.

## 화면 설계

- 기존 요청함 페이지에 “구매 요청 초안” 패널을 추가한다. 새 페이지가 아니므로 기존 페이지별 컨셉아트를 재사용한다.
- 입력 순서: 품목 → 수량 → 예상금액 → 비용센터 → 필요일 → 사유 → 초안 생성.
- 요청 원장에는 구매 건만 품목·수량·금액·비용센터·필요일 요약을 표시한다.
- 기존 `mock/concept/pages/index.html`의 요청함 HTML mock을 동일 정보 구조로 갱신한다.
