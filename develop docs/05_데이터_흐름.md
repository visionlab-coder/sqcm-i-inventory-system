# 웹 애플리케이션 데이터 흐름

## 3계층 왕복 흐름

브라우저 → `frontend` Nginx → 정적 SPA 응답 → 브라우저의 `/api` 요청 → Nginx 리버스 프록시 → `backend` Express → 세션·CSRF·권한 검사 → Service → 매개변수 SQL → `database` PostgreSQL → JSON 응답 → SPA 상태 갱신 → 화면 렌더링.

프론트엔드와 API는 동일 출처 `http://localhost:3000`을 사용하므로 세션 쿠키가 안전하게 왕복한다. 브라우저는 데이터베이스에 직접 접근하지 않는다.

## 읽기 왕복

사용자 요청 → 세션 쿠키 → Nginx `/api` 프록시 → 인증 미들웨어 → 권한 검사 → 검증된 query → 매개변수 SQL → PostgreSQL → DTO 변환 → JSON → SPA 화면.

## 쓰기 왕복

폼 입력 → CSRF 확인 → 스키마 검증 → 권한 검사 → DB transaction → 행 잠금 → 비즈니스 규칙 검증 → 변경과 감사 로그 → commit → JSON 성공 응답 → 필요한 목록 재조회. 실패 시 transaction을 rollback하고 상태 코드와 안전한 메시지를 반환한다.

## 로그인 왕복

이메일·비밀번호 → CSRF → IP+정규화 이메일 속도 제한 → 사용자 조회 → BCrypt 비교 → 실패 누적/계정 잠금 또는 세션 재생성 → 세션 PostgreSQL 저장 → 권한별 대시보드 JSON. 비밀번호와 세션 원문은 로그에 남기지 않는다. 제한 초과는 429와 `Retry-After`를 반환한다.

사용자 초대는 `관리자 재인증 → 조직·부서·역할·범위 검증 → 256-bit 토큰 생성 → SHA-256 해시·48시간 만료 저장 → 초대 링크 → CSRF·비밀번호 정책 → 행 잠금 → 사용자·역할 범위·수락 감사 원자 저장`으로 흐른다. 토큰 원문은 DB·로그에 남기지 않는다.

모든 요청에는 안전한 수신값 또는 UUID request ID를 부여한다. API 오류는 `code`, `message`, `fieldErrors`, `requestId` 계약을 사용하고 응답 `x-request-id`, 구조화 로그, 감사 로그를 같은 값으로 연결한다.

## FR-025 구매 요청 왕복

요청함 구매 폼 → `/api/enterprise/requests` → 인증·CSRF·조직 범위 → Router → `createRequest` → 구매 payload 필드별 정규화·검증 → `workflow_requests` JSONB와 감사 로그 트랜잭션 저장 → 요청 JSON → 요청함 재조회·구매 요약 표시. 실패하면 트랜잭션을 rollback하고 `VALIDATION_ERROR`, 안전한 메시지, 필드명, request ID를 반대 방향으로 반환한다.

## 개발·출시 흐름

Issue → feature branch → 구현 → 단위 테스트 → 문서 갱신 → commit → PR → build → deploy → 세 서비스 health → 로그인·핵심 기능 검사 → 로그 → 성공 또는 rollback.

## 저장 위치 원칙

- 사용자 안내: `client docs`
- 기술·DB·운영: `develop docs`
- 에이전트 지침·프롬프트: `agent docs`
- 실행 코드: `frontend`, `src`; 스키마: `db`; 검증: `test`
