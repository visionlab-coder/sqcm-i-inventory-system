# Phase 27 반납 사진 증빙 설계

## 목표와 범위

RETURN 요청에 반납자·확인자·상태·부속품·메모·사진을 연결하고, 최종 승인 시 자산 상태·배정 종료·반납 원장·감사 로그를 하나의 트랜잭션으로 확정한다.

## 데이터 흐름

1. Browser가 RETURN 초안과 상태·부속품·메모를 전송한다.
2. Controller가 인증·CSRF·조직 범위를 확인하고 Service를 호출한다.
3. Service는 현재 활성 배정자만 반납을 요청할 수 있게 검증한다.
4. 사진 업로드는 JPEG/PNG MIME·시그니처·5 MiB 제한을 검증한다.
5. Repository가 파일 원장·자산 파일·요청 파일·감사를 원자적으로 기록한다.
6. 제출 시 활성 반납 사진의 존재를 다시 확인한다.
7. 최종 승인 시 배정 행을 잠그고 배정 종료·반납 원장·자산 상태·승인·감사·Outbox를 원자적으로 반영한다.

## DB 설계

- `workflow_request_files`: 요청과 파일의 명시적 연결
- `asset_return_records`: 요청, 배정, 자산, 반납자, 확인자, 상태, 메모, 부속품, 사진 파일 보존
- `asset_assignments`: 반납자·확인자·상태·메모·부속품 스냅샷
- `asset_files.file_type`: `RETURN` 허용
- 활성 배정과 사진은 최종 승인 직전 다시 검증하며 실패 시 전체 rollback한다.

## 화면·오류 상태

- RETURN 선택 시에만 반납 필드를 표시하고 사진을 필수화한다.
- 사진이 없거나 PDF·위조 이미지이면 초안 제출을 차단한다.
- 다른 사용자의 초안 사진 업로드는 403으로 거부한다.
- 비정상 상태는 메모를 필수화하고, 저장 실패 메시지로 재시도 방법을 안내한다.

## 인수 기준

- 유효한 PNG/JPEG 사진이 연결된 RETURN 요청만 제출된다.
- 중간 승인에서는 자산과 배정이 변하지 않는다.
- 최종 승인 후 자산은 반납 상태이며 활성 배정이 종료되고 반납 원장이 생성된다.
- 사진·반납 원장·감사 기록은 같은 조직·데이터 범위 정책을 따른다.
