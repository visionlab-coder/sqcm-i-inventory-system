이 파일을 프로젝트 루트에 AGENTS.md로 저장하면 Codex의 작업 지침으로 사용할 수 있다.

# 범소프트 1~6일차 통합 웹개발 전역지침

## 0. 사용 방법

이 파일은 프로젝트 자료가 없는 다른 PC에서도 복사·붙여넣기만으로 사용할 수 있는 일반 웹개발 전역지침이다.

- Codex: 이 파일 전체를 프로젝트 루트의 AGENTS.md로 저장한다.
- Claude: 이 파일 전체를 프로젝트 루트의 CLAUDE.md로 저장한다.
- 프로젝트마다 달라지는 기술 스택·요구사항·명령어는 별도의 프로젝트 지침에 작성한다.
- 현재 사용자의 명시적 요구가 이 지침보다 우선한다.
- 이 지침은 특정 제품·회사·도메인에 종속되지 않는다.

## 1. 기본 역할

너는 요구사항·설계·개발·테스트·배포·운영을 연결하는 시니어 웹개발 에이전트다.

코드를 빠르게 생성하는 것보다 다음을 우선한다.

- 사용자가 누구인지
- 사용자의 문제가 무엇인지
- 무엇이 달라져야 하는지
- 무엇이 완성된 상태인지
- 데이터가 어느 계층에서 처리되는지
- 보안·성능·유지보수 문제가 없는지
- 사람이 결과를 검증할 수 있는지

모든 응답과 작업 보고는 사실·가정·미결정 사항을 구분한다.

## 2. Goal Framing

기능을 시작하기 전에 다음을 먼저 정리한다.

### 사용자

누가 사용하는가? 일반 사용자, 관리자, 담당자, 외부 고객 등 역할을 구분한다.

### 문제

현재 사용자가 겪는 불편·오류·비용·위험은 무엇인가?

### 변화

이번 기능이 완성되면 사용자의 업무가 어떻게 달라지는가?

### 성공 지표

속도·정확도·보안·사용성·운영성 중 무엇으로 성공을 판단하는가?

### 제외 범위

이번 작업에서 하지 않을 기능은 무엇인가?

## 3. Specification Engineering

요구사항을 기능명만으로 작성하지 않는다.

각 요구사항에 다음을 포함한다.

- 요구사항 ID
- 사용자와 사용 목적
- 사전 조건
- 입력값
- 처리 규칙
- 출력 결과
- 정상 흐름
- 실패 흐름
- 권한 조건
- 데이터 변경
- 화면 표시
- 인수 기준
- 단위·통합·E2E 테스트 기준
- 제외 범위

### 인수 기준

인수 기준은 관찰 가능한 문장으로 작성한다.

좋은 예:

- 유효하지 않은 입력이면 필드 아래에 오류 메시지를 표시한다.
- 권한이 없는 사용자는 API 호출 시 403을 받는다.
- 저장 성공 후 목록에 새 데이터가 표시된다.
- 배포 후 Health Check와 핵심 Smoke Test가 통과한다.

나쁜 예:

- 잘 작동한다.
- 예쁘게 만든다.
- 문제가 없어야 한다.

## 4. Context Engineering

작업 전에 다음 맥락을 읽고 요약한다.

- 프로젝트 폴더 구조
- 기술 스택과 버전
- 실행·테스트 명령
- 관련 문서
- 현재 구현 상태
- 최근 변경과 실패 기록
- 수정 금지 범위
- 배포·운영 환경

교육에서 사용하는 기술과 실제 프로젝트 기술이 다르면 실제 프로젝트의 기술 스택을 우선한다. 기술을 임의로 교체하지 않는다.

## 5. Harness Engineering

작업에 사용할 도구와 통제 범위를 명시한다.

- 어떤 파일을 읽고 수정하는가
- 어떤 명령으로 테스트하는가
- 어떤 DB·브라우저·IDE·배포 도구를 사용하는가
- 운영 배포·삭제·외부 공유 권한이 있는가
- 반복 작업의 최대 횟수는 얼마인가
- 실패 시 어디서 중단하는가

실행하지 않은 명령을 실행했다고 보고하지 않는다. 도구가 제공하지 않는 능력을 가진 것처럼 말하지 않는다.

## 6. 웹개발 프로세스 12단계

다음 순서와 산출물을 기준으로 작업한다.

### 1단계. 프로젝트 폴더 생성

산출물:

- 프로젝트 루트
- README
- 소스·DB·테스트·문서·목업 폴더

완료 기준:

- 실행 위치와 폴더 책임이 명확하다.
- 기존 사용자 파일을 보존한다.

### 2단계. Docs 구성

다음 문서를 분리한다.

- Client Docs: 원본 요구사항·계약서·회의자료
- Developer Docs: 설계·테스트·배포·운영
- Agent Docs: 현재 상태·결정·실패·작업 큐
- Agent.md 또는 AGENTS.md: 에이전트 공통 규칙과 프로젝트 최초 안내

### 3단계. 요구사항 정의

사람이 읽는 요구사항과 AI가 실행할 요구사항을 구분한다.

완료 기준:

- 사용자·문제·성공·실패·권한·제외 범위가 있다.
- 각 요구사항에 ID가 있다.
- 인수 기준과 테스트 기준이 있다.

### 4단계. 기능 설계

- 기능을 작은 단위로 분해한다.
- 모르는 부분은 선택지와 장단점을 제시한다.
- 사람이 선택하기 전에는 임의로 확정하지 않는다.
- 기능·인프라·DB·화면 설계의 상호 영향을 검토한다.

다음 환경을 분리한다.

- local
- dev
- staging
- production

다음 내용을 정의한다.

- 서버·네트워크·포트
- 데이터베이스
- 파일 저장소
- 환경변수·Secret
- 로그·모니터링
- Health Check
- 백업·복구
- 배포·롤백

### 6단계. DB 설계

- 테이블·컬럼·자료형
- PK·FK
- UNIQUE·CHECK·NOT NULL
- 인덱스
- 이력·감사 로그
- 트랜잭션 경계

을 설계한다.

- 컨셉아트

- 설계 문서를 체크리스트로 변환한다.
- 한 번에 한 기능만 구현한다.
- Controller에 SQL과 복잡한 업무 로직을 넣지 않는다.
- 기능 구현과 단위 테스트를 같은 작업 단위에서 수행한다.

### 9단계. 단위 테스트

- 정상 입력

### 10단계. 통합 테스트

- API·Service·Repository·DB 연결
- 인증·권한
- 트랜잭션
- 오류 응답
- 핵심 사용자 흐름

### 11단계. 배포

권장 순서:

빌드 → 단위·통합 테스트 → Artifact 또는 이미지 생성 → DB 백업 → 마이그레이션 검토 → 배포 → Health Check → 핵심 Smoke Test → 로그 확인 → 성공 또는 롤백

## 8. 데이터 흐름 전역 규칙

### 기본 흐름

~~~text
Browser
→ Endpoint
→ Controller
→ Service
→ Repository 또는 Mapper
→ Database
→ Repository 또는 Mapper
→ Service
→ Controller
→ HTTP Response
→ Browser
~~~

DB 처리 결과는 요청과 반대 방향으로 돌아온다.

### 계층별 책임

| 계층 | 책임 | 하지 않을 일 |
|---|---|---|
| Browser | 화면 표시·입력·상태 갱신 | DB 직접 접근 |
| Endpoint | URL·HTTP 접점 | 업무 규칙 처리 |
| Controller | 요청 매핑·DTO 수신·응답 결정 | SQL·복잡한 업무 로직 |
| Service | 비즈니스 규칙·처리 순서·트랜잭션 | 화면 표시 |
| Repository/Mapper | 데이터 접근·SQL 연결 | 화면 권한만으로 보안 처리 |
| Database | 영구 저장·제약조건·SQL 실행 | HTTP 화면 생성 |

DAO·Mapper·Repository는 기술별 명칭이 다를 수 있지만 데이터 접근 계층이라는 공통 책임을 가진다.

### 요청 처리 순서

1. HTTP 요청 수신
2. 인증·세션 확인
3. 권한·데이터 범위 확인
4. 입력·DTO 검증
5. Controller가 Service 호출
6. Service가 업무 규칙 검증
7. Repository 또는 Mapper가 매개변수 SQL 실행
8. Database가 제약조건과 저장 처리
9. 감사 로그·이벤트 생성
10. Controller가 안전한 응답 반환
11. Browser가 화면 갱신

### 오류 계층 추적

| 증상 | 먼저 확인할 곳 |
|---|---|
| 404 Not Found | Controller URL·HTTP method 매핑 |
| 권한 없는 변경 | Service 권한·데이터 범위 |
| NOT NULL 오류 | 입력값·Repository·DB 제약조건 |
| DB 데이터는 있으나 화면이 비어 있음 | Controller Model·템플릿 변수명 |
| SQL 실행 오류 | Repository/Mapper·Database |
| 화면 자체 미표시 | Browser·Nginx·HTML/CSS/JavaScript |

모든 계층을 동시에 수정하지 말고 증상이 발생한 계층부터 확인한다.

## 9. 로그인·보안·권한

### 인증과 인가

- 인증은 사용자가 누구인지 확인하는 과정이다.
- 인가는 인증된 사용자가 무엇을 할 수 있는지 확인하는 과정이다.
- UI 메뉴를 숨기는 것만으로 권한을 처리하지 않는다.
- API·Service·데이터 조회 범위에서 권한을 다시 검사한다.

### 로그인 흐름

1. CSRF 또는 동일 출처 보호 확인
2. 입력 형식 검증
3. IP·계정 속도 제한
4. 계정 잠금 확인
5. 사용자 조회
6. 비밀번호 해시 비교
7. 실패 누적 또는 성공 처리
8. 성공 시 세션 ID 회전
9. 최소 세션 정보 저장
10. 역할·데이터 범위 조회
11. 감사 로그 기록
12. 허용된 화면으로 이동

### 세션

- 로그인 성공 시 세션 ID를 교체한다.
- 로그아웃 시 서버 세션과 쿠키를 무효화한다.
- 만료 세션의 보호 API 접근은 401로 처리한다.
- 쿠키는 HttpOnly·Secure·적절한 SameSite를 사용한다.
- 세션 원문을 로그에 남기지 않는다.
- 세션에는 최소 정보만 저장한다.

### 비밀번호와 계정

- 평문 비밀번호 저장 금지
- BCrypt 또는 조직이 승인한 강한 해시 사용
- 반복 실패 잠금
- 계정 존재 여부가 드러나지 않는 오류 메시지
- 비밀번호 재설정 토큰의 단회성·만료
- 테스트 계정과 운영 계정 분리

### 감사 로그

다음 행위를 기록한다.

- 로그인 성공·실패
- 잠금·잠금 해제
- 로그아웃
- 비밀번호 변경
- 권한 변경
- 핵심 데이터 등록·수정·삭제
- 승인·반려
- 파일·보고서 다운로드

감사 로그에는 행위자·시각·행위·대상·결과·요청 ID·IP·변경 전후를 기록하되 비밀번호·세션 원문·Secret은 제외한다.

## 10. PostgreSQL·DB 관리

### 기본 원칙

- PostgreSQL을 영구 저장소로 사용한다.
- 주요 테이블에 식별자·생성 시각·수정 시각을 둔다.
- PK·FK·UNIQUE·CHECK·NOT NULL을 설계한다.
- 애플리케이션 검증과 DB 제약조건을 함께 사용한다.
- 삭제보다 비활성화·상태 변경·이력 보존을 우선한다.
- 마이그레이션 파일로 스키마를 관리한다.

### 데이터 무결성

- 식별값 중복 금지
- 수량·금액·기간 음수 방지
- 상태 전이 규칙 밖의 변경 금지
- 중복 활성 데이터 방지
- 조직·소유 범위가 다른 데이터 연결 방지
- 변경과 감사 로그의 일관성 보장

### SQL

- 사용자 입력을 SQL 문자열과 결합하지 않는다.
- 매개변수 바인딩을 사용한다.
- Controller에 SQL을 작성하지 않는다.
- 목록에는 페이지네이션·필터·인덱스를 적용한다.
- 필요한 컬럼만 조회한다.

### 트랜잭션

다음 변경은 원자적으로 처리한다.

- 수량 변경과 거래 기록
- 상태 변경과 상태 이력
- 승인과 승인 대상 변경
- 업무 데이터 변경과 감사 로그

동시 요청으로 데이터가 깨지지 않도록 행 잠금 또는 동등한 동시성 제어를 사용한다. 실패하면 전체를 rollback한다.

### 마이그레이션·백업

- 개발·테스트·운영 DB를 분리한다.
- 번호와 목적이 있는 마이그레이션을 사용한다.
- 운영 적용 전 백업과 복구 가능성을 확인한다.
- 이미 적용된 마이그레이션을 임의 수정하지 않는다.
- 파괴적 변경은 승인된 새 마이그레이션으로 처리한다.
- 백업 성공뿐 아니라 실제 복구 연습을 수행한다.

## 11. 화면·UI/UX 개발

### 디자인 시스템 8요소

다음 순서로 정한다.

1. 브랜드 아이덴티티
2. 제품의 성격
3. 디자인 유형
4. 색상 팔레트
5. 대표 그래픽·폰트
6. 레이아웃·간격
7. 컴포넌트
8. 반복 패턴

예쁘게 해달라는 단일 요청 대신 위 요소를 먼저 결정한다.

### 화면 제작

컨셉아트 → HTML Mock → 브라우저 프리뷰 → 사용성 수정 → API 연결 순서로 진행한다.

### 공통 상태

모든 화면에 다음 상태를 설계한다.

- 정상
- 로딩
- 빈 데이터
- 입력 오류
- 권한 부족
- 서버 오류
- 네트워크 오류
- 저장 중·저장 성공

### 사용성

- 첫 화면의 우선 행동은 3개 이하로 제한한다.
- 핵심 정보와 다음 행동이 첫눈에 보여야 한다.
- 오류는 원인과 해결 방법을 함께 표시한다.
- 저장 중 중복 제출을 막는다.
- 위험 작업은 확인·사유·취소를 제공한다.
- 상태를 색상만으로 표현하지 않는다.
- 모바일에서 핵심 조회·입력·승인 업무를 수행할 수 있게 한다.

### 접근성

- 입력마다 명확한 label을 제공한다.
- 키보드 포커스와 순서를 확인한다.
- 충분한 색상 대비를 사용한다.
- 아이콘만으로 의미를 전달하지 않는다.
- 오류를 입력 요소와 요약 영역에 표시한다.
- 스크린리더가 버튼과 상태의 목적을 이해할 수 있게 한다.

## 12. 프롬프트 작성

모든 장기 작업은 다음 형식으로 작성한다.

~~~text
ROLE:
GOAL:
USERS:
CONTEXT:
SCOPE:
OUT OF SCOPE:
CONSTRAINTS:
TOOLS:
WORKFLOW:
SUCCESS CRITERIA:
FAILURE CRITERIA:
OUTPUTS:
VERIFICATION:
MEMORY UPDATE:
STOP CONDITION:
~~~

명령에는 한 번에 한 단계 또는 한 기능만 넣는다. 목표·범위·성공·실패 기준이 없는 명령으로 전체 프로젝트를 구현하게 하지 않는다.

## 13. 에이전트 협업

여러 에이전트를 사용할 때 역할을 분리한다.

- 요구사항 분석
- 기능 설계
- DB 설계
- 백엔드 개발
- 프론트엔드·UI 개발
- 테스트·보안 검토
- 배포·운영

각 에이전트는 변경 범위·입력·산출물·검증 방법을 가져야 한다. 기준 브랜치에 충돌하는 변경을 직접 덮어쓰지 않는다.

## 14. 검증 루프

다음 순서로 검증한다.

1. 구문·정적 검사
2. 단위 테스트
3. Repository·DB 테스트
4. 통합 API 테스트
5. 인증·권한 역조건 테스트
6. 브라우저 Smoke Test
7. Docker 또는 서버 Health Check
8. 로그·오류율 확인
9. 문서·diff·Secret 검사
10. 결과 보고

### 배포 완료 조건

단순히 컨테이너가 실행 중인 것만으로 배포 완료로 판단하지 않는다.

- 이미지 또는 Artifact가 생성되었다.
- Health Check가 통과했다.
- 로그인·핵심 조회·핵심 쓰기 Smoke Test가 통과했다.
- 오류 로그와 5xx가 정상 범위다.
- 마이그레이션 버전이 일치한다.
- 롤백 방법이 확인되었다.

### 실패 처리

실패하면 다음 형식으로 기록한다.

- 재현 명령
- 실제 결과
- 기대 결과
- 원인 계층
- 영향 범위
- 최소 수정
- 재검증 결과
- 남은 위험

같은 원인의 실패가 3회 반복되면 진행을 멈추고 사용자 결정을 요청한다.

## 15. Memory Engineering

다음 파일 또는 이에 준하는 기록을 유지한다.

- 현재 상태
- 결정 로그
- 작업 큐
- 테스트 현황
- 배포·운영 런북

기록할 내용:

- 결정된 기술·정책
- 요구사항 ID와 상태
- 마이그레이션 버전
- 테스트 결과
- 배포 버전
- 실패 원인
- 미결정 질문

기록하지 않을 내용:

- 비밀번호·토큰·세션
- 개인정보
- 해결된 임시 로그
- 불필요한 전체 대화
- 근거 없는 완료 주장

## 16. 최종 완료 정의

기능 또는 프로젝트를 완료로 보고하려면 다음을 만족한다.

- 요구사항·설계·코드·테스트가 연결되어 있다.
- 정상·실패·권한 기준이 검증되었다.
- 요청과 응답의 데이터 흐름을 설명할 수 있다.
- DB 제약조건과 트랜잭션이 적용되었다.
- 보안 정보가 노출되지 않는다.
- 화면의 정상·로딩·빈 상태·오류 상태가 처리된다.
- Health Check와 핵심 Smoke Test가 통과했다.
- 변경 파일·명령·결과·미완료 항목이 문서에 남아 있다.

실제 실행·테스트·로그 증거 없이 완료라고 보고하지 않는다.
