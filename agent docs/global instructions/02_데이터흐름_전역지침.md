# 데이터 흐름 전역지침

## 1. 기본 왕복 흐름

~~~text
Browser
→ Endpoint
→ Controller
→ Service
→ Repository 또는 Mapper
→ Database
→ Repository 또는 Mapper
→ Service
→ Controller
→ HTTP Response
→ Browser
~~~

브라우저의 요청과 DB 처리 결과는 반대 방향으로 돌아온다.

## 2. 계층 책임

| 계층 | 책임 | 금지 |
|---|---|---|
| Browser | 화면 표시·사용자 입력·화면 상태 | DB 직접 접근 |
| Endpoint | URL·HTTP 접점 | 업무 규칙 구현 |
| Controller | 요청 매핑·입력 수신·응답 결정 | SQL·복잡한 업무 로직 |
| Service | 비즈니스 규칙·처리 순서·트랜잭션 | 화면 표시 책임 |
| Repository/Mapper | 데이터 접근·SQL 연결 | 사용자 권한 정책 단독 판단 |
| Database | 영구 저장·제약조건·SQL 실행 | HTTP 화면 생성 |

DAO·Mapper·Repository는 기술에 따라 명칭과 구현 방식이 달라질 수 있으나, 데이터 접근 계층이라는 공통 책임으로 이해한다.

## 3. 요청 처리 순서

1. HTTP 요청 수신
2. 세션·인증 확인
3. 권한·조직 범위 확인
4. DTO 또는 입력 스키마 검증
5. Controller가 Service 호출
6. Service가 업무 규칙 검증
7. Repository/Mapper가 매개변수 SQL 실행
8. Database가 제약조건과 저장 처리
9. 감사 로그와 필요한 이벤트 생성
10. Service 결과를 Controller가 응답으로 변환
11. Browser가 화면 상태를 갱신

## 4. 읽기와 쓰기

### 읽기

조회는 필요한 컬럼만 반환하고 필터·정렬·페이지네이션을 사용한다.

### 쓰기

변경은 Command 단위로 설계한다.

- 등록
- 배정
- 반납
- 승인
- 상태 전환
- 폐기

상태를 무제한 수정하는 일반 PATCH 하나로 업무 규칙을 우회하지 않는다.

## 5. 트랜잭션

다음 작업은 하나의 원자적 단위로 처리한다.

- 재고 감소와 대여 생성
- 반납 처리와 재고 복원
- 자산 상태 변경과 상태 이력
- 승인 처리와 업무 데이터 변경
- 변경 데이터와 감사 로그 생성

실패하면 전체를 rollback한다.

동시 요청으로 재고가 초과되지 않도록 대상 행 잠금 또는 동등한 동시성 제어를 사용한다.

## 6. 오류 위치 추적

| 증상 | 우선 확인 |
|---|---|
| 404 | Controller URL·HTTP method mapping |
| 권한 없는 데이터 변경 | Service 권한·조직 범위 |
| NOT NULL 오류 | 입력값·Repository·DB 제약조건 |
| DB에는 데이터가 있으나 화면이 비어 있음 | Controller Model 이름·템플릿 변수명 |
| SQL 생성·실행 오류 | Repository/Mapper·Database 경계 |
| 화면 자체가 표시되지 않음 | Browser·Nginx·HTML/CSS/JS |

오류를 발견하면 모든 파일을 임의로 수정하지 말고 증상이 발생한 계층부터 확인한다.

## 7. 오류 응답

오류 응답은 다음 정보를 포함한다.

- 안전한 오류 코드
- 사용자가 이해할 메시지
- 필드별 오류
- 요청 ID
- HTTP 상태 코드

비밀번호·토큰·내부 SQL·스택트레이스를 사용자에게 노출하지 않는다.
