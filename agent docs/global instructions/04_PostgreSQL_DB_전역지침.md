# PostgreSQL·DB 관리 전역지침

## 1. 설계 원칙

- PostgreSQL을 시스템의 영구 데이터 저장소로 사용한다.
- 모든 업무 테이블에 식별자·생성 시각·수정 시각을 둔다.
- PK·FK·UNIQUE·CHECK·NOT NULL을 설계 단계에서 명시한다.
- 애플리케이션 검증과 DB 제약조건을 함께 사용한다.
- 삭제보다 비활성화와 이력 보존을 기본으로 한다.
- 스키마 변경은 순번이 있는 마이그레이션으로 관리한다.

## 2. 데이터 무결성

- 비품 코드·이메일 등 식별값 중복 금지
- 수량·금액·기간의 음수 방지
- 가용 수량이 0보다 작아지지 않게 함
- 총수량이 대여 중 수량보다 작아지지 않게 함
- 활성 대여 중복 방지
- 반납 완료 건의 중복 반납 방지
- 상태 전이 규칙 밖의 변경 차단
- 조직 범위가 다른 데이터 연결 차단

## 3. SQL

- 사용자 입력과 SQL을 문자열 결합하지 않는다.
- 모든 입력은 매개변수 바인딩한다.
- Repository/Mapper가 SQL 접근을 담당한다.
- Controller에 SQL을 작성하지 않는다.
- 목록 조회는 페이지네이션과 인덱스를 사용한다.
- 필요한 컬럼만 조회한다.

## 4. 트랜잭션

다음 변경은 같은 트랜잭션으로 묶는다.

- 재고 감소와 대여 생성
- 재고 복원과 반납 기록
- 상태 변경과 상태 이력
- 승인과 승인 대상 변경
- 업무 변경과 감사 로그

동시성 때문에 수량이 초과되지 않도록 행 잠금 또는 적절한 동시성 제어를 사용한다.

## 5. 마이그레이션

- 개발·테스트·운영 DB를 분리한다.
- 마이그레이션 파일의 번호와 목적을 명확히 한다.
- 운영 적용 전에 백업과 복구 가능성을 확인한다.
- 이미 적용된 마이그레이션을 임의로 수정하지 않는다.
- 파괴적 변경은 새 마이그레이션과 승인 절차를 사용한다.
- 시드 데이터와 운영 데이터를 구분한다.

## 6. 백업·운영

- 정기 백업 주기와 보존 기간을 문서화한다.
- 백업 성공만 확인하지 말고 실제 복구 연습을 한다.
- DB 용량·느린 쿼리·연결 수·오류를 관찰한다.
- 감사 로그는 일반 사용자가 수정·삭제하지 못하게 한다.
- 배포 전 DB 버전과 애플리케이션 버전의 호환성을 확인한다.
