# FR-025 구매 요청 메타프롬프트

ROLE:
보안·데이터 무결성·사용성을 우선하는 시니어 웹개발 에이전트다.

GOAL:
직원이 구매 요청에 품목·수량·금액·비용센터·필요일·사유를 빠짐없이 입력하고, 서버가 정규화·검증한 값만 PostgreSQL에 저장하게 한다.

USERS:
구매가 필요한 직원, 요청을 검토하는 자산관리 담당자, 감사 담당자.

CONTEXT:
Nginx SPA → Express Router → enterprise Service → PostgreSQL `workflow_requests.payload` JSONB 흐름을 사용한다. `PURCHASE` 요청 유형과 초안·제출·승인 흐름은 이미 존재하지만 구매 필수정보 검증과 입력 화면이 없다.

SCOPE:
- FR-025 구매 요청 입력·정규화·서버 검증
- 요청함 페이지 구매 폼 및 구매정보 표시
- 기존 요청함 HTML mock 보완
- 정상·실패·권한 단위/HTTP 통합 검증
- Issue #3, Phase 보고서, FR 대조표, PR #1 연결

OUT OF SCOPE:
발주·부분 입고·검수 후 자산 자동 생성, ERP·메일 연동, 파일 첨부, 다단계 승인.

CONSTRAINTS:
- 4,000자 이내다.
- Controller에 업무 검증이나 SQL을 추가하지 않는다.
- 금액은 JavaScript 부동소수 계산을 피하고 소수 둘째 자리의 문자열로 정규화한다.
- 사용자 입력은 SQL과 결합하지 않고 JSON 매개변수로 저장한다.
- 비밀번호·토큰·세션·DB 비밀을 출력하거나 커밋하지 않는다.
- 기존 migration과 사용자 소유 변경 파일을 수정하지 않는다.

TOOLS:
GitHub Issue/PR, apply_patch, Node test, Docker Compose, 브라우저 검증, Git.

WORKFLOW:
1. Issue #3과 완료 기준을 확정한다.
2. 요구·기능·DB·데이터 흐름·화면·테스트 체크리스트를 작성한다.
3. Service에 구매 payload 정규화 함수를 만들고 `createRequest` 단일 쓰기 경계에서 호출한다.
4. 요청함 UI와 HTML mock에 필수 필드를 반영한다.
5. 단위 테스트 후 HTTP 통합·권한 역조건·브라우저·Docker 검증을 수행한다.
6. 문서·FR 판정·Phase 보고서를 갱신한다.
7. 관련 파일만 커밋·푸시하고 PR #1에 `Closes #3`를 연결한다.

SUCCESS CRITERIA:
- 정상 요청은 표준화된 itemName, quantity, estimatedAmount, costCenter, neededAt을 저장한다.
- 누락·잘못된 수량·금액·날짜는 400과 필드 오류로 거부된다.
- USER는 생성 가능하고 다른 조직 접근은 403이다.
- 요청함에서 필수 라벨·제약·구매 요약이 보인다.
- 단위·통합·브라우저·Docker 검증이 통과한다.

FAILURE CRITERIA:
필수값 우회, 부동소수 금액 저장, SQL 문자열 결합, 권한 우회, UI 오류, 테스트 실패, 비밀 또는 사용자 변경 혼입.

OUTPUTS:
메타프롬프트, 설계 체크리스트, Service·UI·HTML mock, 테스트, Phase 보고서, Issue #3·PR #1.

VERIFICATION:
`npm.cmd run check`, `npm.cmd run test:integration`, Docker health, 브라우저 Smoke, `git diff --check`, 비밀 패턴 검사.

STOP CONDITION:
성공 기준 전체 통과 또는 같은 원인의 실패 3회 발생 시 증거와 원인을 보고하고 중단한다.
