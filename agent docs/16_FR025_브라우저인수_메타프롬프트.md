# Phase 23 — FR-025 브라우저 인수 메타프롬프트

ROLE:
서원토건 비품관리 시스템의 요구사항·화면·API·DB·감사를 실제 사용자 흐름으로 검증하는 시니어 QA 웹개발 에이전트다.

GOAL:
기존 Issue #3의 마지막 조건인 FR-025 직원 구매 요청 브라우저 인수를 완료하고 코드·테스트와 불일치하는 오래된 부분 완료 판정을 바로잡는다.

USERS:
품목 구매를 요청하는 직원과 요청을 검토하는 담당자다.

CONTEXT:
Service 검증, 요청함 UI, PostgreSQL JSONB 저장, 감사로그, 단위·HTTP 통합은 이미 통과했다. 이전 Phase는 브라우저 연결 오류 때문에 부분 완료였다. Docker는 frontend/backend/database 3서비스다.

SCOPE:
직원 로그인, 요청함 이동, 품목·수량·예상금액·비용센터·필요일·요청 사유 6개 필드, 정상 초안 생성 메시지, 원장 구매 요약, DB payload·감사, desktop/mobile·공식 로고·콘솔, 테스트 데이터 정리, 문서 판정 동기화.

OUT OF SCOPE:
다단계 승인정책, ERP·메일 연동, 운영 배포, 실제 회사 구매 요청 생성, 기능 재설계.

CONSTRAINTS:
로컬 테스트 환경에 고유 표식을 가진 데이터만 생성한다. 생성 ID·조직·유형을 확인한 뒤 해당 테스트 데이터만 정리한다. 사용자 소유 AGENTS.md·CLAUDE.md·전역지침은 수정·커밋하지 않는다. 화면·목업에 제작 메타데이터를 노출하지 않는다. 4,000자 이내다.

TOOLS:
앱 내 브라우저, Docker Compose, PostgreSQL, Node.js 테스트, Git/GitHub.

WORKFLOW:
1. Issue #3과 기존 인수 기준을 확인한다.
2. 직원 계정으로 로그인하고 요청함의 6개 label·HTML 제약을 확인한다.
3. 고유 품목명으로 정상 구매 요청 초안을 생성한다.
4. 성공 메시지와 품목·수량·금액·비용센터·필요일 요약을 확인한다.
5. DB에서 정규화 payload와 REQUEST_CREATED 감사를 확인한다.
6. desktop/mobile 레이아웃, 공식 반전 로고, 콘솔 오류를 확인한다.
7. 식별된 테스트 요청·감사만 짧은 트랜잭션으로 정리하고 잔존 0을 확인한다.
8. 전체 단위·통합·Docker health·diff·Secret 검사를 재실행한다.
9. Phase 보고서와 FR 대조표를 완료 31·부분 4로 동기화하고 commit/push/PR/Issue를 갱신한다.

SUCCESS CRITERIA:
6개 필드와 제약이 실제 화면에 보인다. 정상 제출 후 성공 메시지와 원장 구매 요약이 보인다. DB payload·감사와 화면 값이 일치한다. 모바일 수평 넘침과 콘솔 오류가 없다. 테스트 데이터 잔존이 0이고 전체 게이트와 CI가 통과한다.

FAILURE CRITERIA:
필드 누락, UI/API/DB 값 불일치, 감사 누락, 실제 사용자 데이터 변경, 테스트 데이터 잔존, 근거 없는 완료 판정 중 하나라도 발생한다.

OUTPUTS:
브라우저 스크린샷, DB·감사 증거, 갱신된 설계 체크리스트·Phase 16/23 보고서·FR 대조표·검증 보고서, commit/push/PR/Issue 기록.

VERIFICATION:
브라우저 DOM→정상 제출→DB/감사→모바일/콘솔→정리→정적·단위→HTTP 통합→Docker health/log→문서·diff·Secret→CI 순서다.

MEMORY UPDATE:
FR-025 완료, 기업형 완료 31·부분 4, 남은 외부 결정과 테스트 수치를 Agent 메모리에 기록한다.

STOP CONDITION:
같은 원인 실패 3회, 테스트 대상 식별 불가, 외부 정책 결정 또는 실제 사용자 데이터 변경 위험이 생기면 중단하고 보고한다.
