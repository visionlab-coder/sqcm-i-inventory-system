# 비품관리시스템 전체 요구사항 및 전 과정 설계

문서 상태: 구현 기준 초안  
목적: Codex가 기업용 비품관리시스템을 단계별로 설계·구현·검증할 때 참조하는 AI용 기준 문서  
대상: 기업·공공기관·다지점 조직의 비품·IT장비·시설자산 관리  
권장 스택: React/Next.js + TypeScript, Java 21 + Spring Boot, PostgreSQL, Flyway, Docker

> 이 문서는 요구사항, 데이터 흐름, 로그인, DB, 화면, 개발, 테스트, 배포, 운영을 하나의 기준으로 연결한다. 구현 중 요구사항과 충돌하면 임의로 진행하지 말고 충돌 내용과 선택지를 기록한다.

## 0. 설계 원칙

1. 비품의 현재 상태뿐 아니라 구매부터 폐기까지의 생애주기 이력을 관리한다.
2. 자산의 상태·소유자·부서·위치는 승인 가능한 업무 흐름으로 변경한다.
3. 모든 핵심 변경은 누가, 언제, 무엇을, 어디서, 왜 변경했는지 추적한다.
4. 처음 사용하는 직원도 3분 안에 핵심 업무를 시작할 수 있게 한다.
5. 화면 숨김만 믿지 않고 API와 Service 계층에서 권한을 다시 검사한다.
6. PostgreSQL의 제약조건·트랜잭션·인덱스를 활용한다.
7. AI에게 전체를 한 번에 구현시키지 않고 작은 기능 단위로 구현·테스트·검토한다.
8. 운영 장애를 전제로 로그·헬스체크·백업·롤백을 설계한다.

## 1. Goal Framing

### 1.1 사용자

| 사용자 | 주요 목적 |
|---|---|
| 일반 직원 | 내 비품 조회, 수령·반납 요청, 고장·분실 신고 |
| 부서 담당자 | 부서 비품 조회, 배정·반납 승인, 실사 |
| 자산 관리자 | 자산 등록, 라벨, 배정·이동·수리·폐기 |
| 구매 담당자 | 구매 요청, 발주, 입고, 검수 |
| 재무 담당자 | 취득가, 비용센터, 폐기 증빙, 회계정보 |
| IT·시설 담당자 | 장비 사양, 유지보수, 수리, 위치 |
| 감사 담당자 | 자산 이력, 승인 이력, 변경 로그, 보고서 |
| 시스템 관리자 | 조직·사용자·역할·정책·기준정보 |
| 경영진 | 자산 현황, 비용, 미배정·노후·분실 현황 |

### 1.2 달라져야 하는 상태

- 모든 비품에 고유 자산번호와 현재 상태가 있다.
- 자산이 누구에게, 어느 부서에, 어느 위치에 있는지 즉시 확인된다.
- 구매·입고·검수·배정·이동·수리·반납·폐기 이력이 연결된다.
- 직원은 복잡한 메뉴를 몰라도 검색·요청·확인을 완료한다.
- 관리자는 승인 대기·분실·수리 지연·실사 불일치를 대시보드에서 발견한다.
- 감사 담당자는 데이터 변경자와 변경 전·후 값을 재현할 수 있다.

### 1.3 성공 지표

| 지표 | 1차 목표 |
|---|---|
| 자산 식별률 | 등록 대상의 98% 이상이 자산번호·상태·소유부서를 보유 |
| 위치 확인 | 검색 후 10초 안에 담당자·부서·위치 확인 |
| 요청 처리 | 직원이 3단계 이내로 요청 제출 |
| 감사 추적 | 핵심 상태 변경 100%가 감사 로그에 기록 |
| 중복 자산번호 | DB 제약조건으로 0건 |
| 품질 | PR 병합 전 테스트·정적 검사 통과 |
| 접근성 | 키보드 탐색·명확한 오류·충분한 대비 지원 |

### 2.3 기능 요구사항

#### 사용자·조직

- FR-001 법인, 본부, 부서, 팀, 비용센터, 근무지를 관리한다.
- FR-002 사용자를 등록·초대·비활성화하고 부서를 연결한다.
- FR-003 사용자 역할과 데이터 범위를 관리한다.
- FR-004 조직 변경 후에도 과거 자산 이력은 보존한다.

#### 인증·권한

- FR-005 안전한 로그인·로그아웃·세션 만료를 제공한다.
- FR-006 비밀번호 재설정, 잠금, 레이트리밋, MFA 확장 구조를 제공한다.
- FR-007 사용자가 허용된 조직·부서·기능만 조회·변경하게 한다.
- FR-008 민감한 관리자 작업은 재인증 또는 추가 승인을 요구할 수 있다.

#### 기준정보·자산 원장

- FR-009 자산 유형, 모델, 공급업체, 상태, 사유, 위치를 관리한다.
- FR-010 자산번호는 조직 내에서 중복될 수 없다.
- FR-011 자산 등록 시 유형, 명칭, 취득일, 취득가, 상태, 위치를 기록한다.
- FR-012 IT 자산은 제조번호·MAC·운영체제·사양을 확장 속성으로 기록한다.
- FR-013 사진·영수증·검수서·폐기증빙을 자산과 연결한다.
- FR-014 자산 상세에서 현재 상태와 전체 이력을 함께 보여준다.
- FR-015 자산번호·제조번호·사용자·부서·위치·상태·기간으로 검색한다.
- FR-016 기준정보는 삭제보다 비활성화와 이력 보존을 기본으로 한다.

#### 요청·승인·배정

- FR-017 직원은 배정·반납·이동·수리·분실·구매 요청을 제출한다.
- FR-018 요청은 초안·제출·검토·승인·반려·취소·완료 상태를 가진다.
- FR-019 승인자는 요청 대상과 권한에 따라 승인·반려하고 사유를 남긴다.
- FR-020 승인 단계는 조직 정책에 따라 1단계 이상으로 설정한다.
- FR-021 승인 결과에 따라 자산 상태와 배정 정보를 하나의 트랜잭션으로 변경한다.
- FR-022 동일 자산에 유효한 책임 배정이 중복되지 않게 한다.
- FR-023 이동 시 이전 배정 종료와 새 배정 시작을 기록한다.
- FR-024 반납 시 반납자·확인자·상태·사진·메모를 기록한다.

#### 구매·검수·수리·폐기·실사

- FR-025 구매 요청에 품목·수량·금액·비용센터·필요일·사유를 입력한다.
- FR-026 승인 후 발주·부분 입고·검수를 관리한다.
- FR-027 검수 전 입고품은 사용 가능 자산으로 배정할 수 없다.
- FR-028 수리 요청에 증상·우선순위·담당자·업체·비용·이력을 기록한다.
- FR-029 분실·도난은 즉시 감사 이벤트와 알림을 생성한다.
- FR-030 폐기는 승인과 증빙 확인 후 최종 상태로 변경한다.
- FR-031 실사 계획·대상·결과·불일치 사유·확정자를 기록한다.
- FR-032 대시보드에서 전체·사용 중·미배정·수리·분실·폐기 대기를 보여준다.
- FR-033 부서·위치·유형·상태·기간별 보고서를 제공한다.
- FR-034 CSV 다운로드는 권한을 검사하고 다운로드 이력을 남긴다.
- FR-035 감사 담당자는 핵심 행위와 변경 전·후 값을 검색한다.

## 3. 권한 모델

### 3.1 역할

| 역할 | 범위 | 핵심 권한 |
|---|---|---|
| EMPLOYEE | 본인 | 본인 자산 조회, 요청·신고 |
| DEPARTMENT_MANAGER | 소속 부서 | 부서 조회, 배정·반납 승인 |
| ASSET_OPERATOR | 담당 조직 | 원장·배정·이동·실사·수리 |
| PROCUREMENT | 담당 조직 | 구매·발주·입고·공급업체 |
| FINANCE | 담당 조직 | 취득가·비용센터·폐기증빙 |
| IT_FACILITY | 담당 조직 | 사양·수리·위치 |
| AUDITOR | 승인 범위 | 읽기 전용 감사·보고서 |
| SYSTEM_ADMIN | 전체 | 사용자·역할·정책·기준정보 |
| EXECUTIVE_VIEWER | 지정 범위 | 대시보드·보고서 읽기 |

### 3.2 권한 계산

사용자 → 역할 → 기능 권한 → 조직 범위 순서로 권한을 계산한다.

- 기능 예: asset.read, asset.create, asset.assign, asset.dispose
- 데이터 범위: 전체, 법인, 부서, 본인, 지정 위치
- 행위 범위: 조회, 생성, 수정, 승인, 폐기, 다운로드
- 요청 생성자는 자신이 만든 요청을 승인할 수 없게 한다.
- UI에서 메뉴를 숨겨도 백엔드는 모든 요청에 권한을 재검사한다.

## 4. 핵심 업무 로직

### 4.1 자산 생애주기

~~~text
구매요청 → 승인 → 발주 → 입고 → 검수대기 → 사용가능
→ 배정 → 사용중 → 이동/반납/수리
→ 사용가능 또는 폐기대기 → 폐기승인 → 폐기완료
~~~

### 4.2 자산 상태

| 상태 | 의미 | 다음 상태 |
|---|---|---|
| DRAFT | 등록 중 | ACTIVE, CANCELLED |
| RECEIVED | 입고됐지만 검수 전 | INSPECTION_PENDING |
| INSPECTION_PENDING | 검수 대기 | AVAILABLE, REPAIR |
| AVAILABLE | 배정 가능 | ASSIGNED, DISPOSE_PENDING |
| ASSIGNED | 책임 대상에 배정 | IN_USE, RETURNED, LOST, REPAIR |
| IN_USE | 실제 사용 중 | TRANSFER_PENDING, RETURNED, LOST, REPAIR |
| TRANSFER_PENDING | 이동·인수인계 중 | IN_USE, AVAILABLE, CANCELLED |
| RETURNED | 반납 접수 | AVAILABLE, REPAIR, DISPOSE_PENDING |
| REPAIR | 수리 중 | AVAILABLE, IN_USE, DISPOSE_PENDING |
| LOST | 분실·도난 | FOUND, DISPOSE_PENDING |
| DISPOSE_PENDING | 폐기 승인 대기 | DISPOSED, AVAILABLE, REJECTED |
| DISPOSED | 폐기 완료 | 종료 |
| CANCELLED | 취소 | 종료 |

상태 변경은 AssetService.changeStatus 같은 단일 진입점에서 처리한다. 화면에서 상태값을 직접 저장하지 않는다.

### 4.3 배정·반납·실사

1. 직원 또는 담당자가 배정 요청을 작성한다.
2. 자산이 AVAILABLE인지, 중복 유효 배정이 없는지 검증한다.
3. 필요한 경우 부서장·자산 담당자에게 승인을 보낸다.
4. 승인 시 요청 승인, 기존 배정 종료, 신규 배정 생성, 상태 변경, 이력, 감사 로그를 한 트랜잭션으로 처리한다.
5. 반납 시 자산번호·부속품·상태·사진을 확인하고, 사용 가능·수리·폐기 대기로 분기한다.
6. 실사는 계획 생성 → 대상 생성 → QR/검색 확인 → 예상·실제 위치 비교 → 불일치 사유 → 담당자·승인자 확정 순서로 진행한다.

## 6. 데이터 흐름 관리

### 6.1 기본 요청 흐름

~~~text
사용자
  ↓ HTTPS
브라우저(Next.js)
  ↓ 화면 검증·API 호출
Reverse Proxy / API Gateway
  ↓ HTTPS·보안 헤더·Request ID
Spring Controller
  ↓ 인증·DTO·형식 검증
Application Service
  ↓ 권한·조직 범위·상태 전이 검증
Transaction
  ↓ 원자적 변경
Repository / Query Layer
  ↓ 파라미터 바인딩 SQL
PostgreSQL
  ↓
Audit Log / Outbox Event
  ↓ 알림·연동·통계
JSON 응답 → 화면 상태 갱신
~~~

### 6.2 관리 규칙

- 조회는 필터·정렬·페이지네이션을 제공한다.
- 변경은 목적별 Command API로 만든다. 예: POST /api/v1/assets/{id}/assignments
- 상태 변경을 무제한 PATCH로 허용하지 않고 목적별 API를 사용한다.
- 모든 요청에 correlation ID를 연결한다.
- 오류 응답은 code, message, fieldErrors, requestId를 포함한다.
- 외부 알림과 연동은 Outbox 패턴으로 유실을 방지한다.
- 재시도에 대비해 변경 요청에 idempotency key를 적용한다.
- 자산 상태·배정·반납·이력은 하나의 트랜잭션으로 처리한다.

## 7. 로그인·인증·인가

### 7.1 방식

1. 기업 환경에서는 SSO/OIDC를 우선한다.
2. MVP는 사번/이메일 + 비밀번호로 시작할 수 있다.
3. 비밀번호는 평문 저장 금지, Argon2id 또는 조직 표준 BCrypt 해시를 사용한다.
4. MFA는 TOTP·이메일·보안키로 확장 가능하게 한다.
5. 세션 쿠키는 HttpOnly, Secure, 적절한 SameSite를 사용한다.

### 7.2 로그인 흐름

~~~text
로그인 화면
  → 사용자명·비밀번호 형식 검증
  → 계정 상태·시도 제한 확인
  → 해시 검증
  → MFA 필요 여부 확인
  → MFA 검증
  → 세션 ID 재발급
  → 안전한 쿠키 저장
  → 역할·조직 범위 조회
  → 감사 로그
  → 대시보드 이동
~~~

### 7.3 실패·보안

- 존재하지 않는 계정 여부가 노출되지 않도록 오류 메시지를 통일한다.
- 반복 실패는 IP·계정·조직 단위의 레이트리밋과 잠금으로 방어한다.
- 로그인 성공 시 세션 ID를 교체한다.
- 로그아웃 시 서버 세션과 쿠키를 모두 무효화한다.
- 세션 만료 후 보호 API는 401을 반환하고 로그인 화면으로 이동한다.
- 비밀번호 재설정 토큰은 단회성·만료·해시 저장을 적용한다.
- 민감한 관리자 작업은 재인증을 요구할 수 있다.
- 로그인·로그아웃·실패·잠금·MFA·비밀번호 변경·권한 변경을 감사한다.

## 8. PostgreSQL DB 설계

### 8.1 기본 원칙

- 주요 테이블은 id uuid primary key, created_at, updated_at을 가진다.
- 다법인 확장을 위해 업무 테이블에 organization_id를 둔다.
- 날짜·시간은 timestamptz로 저장한다.
- 상태와 사유는 코드 테이블 또는 통제된 도메인 코드로 관리한다.
- 삭제보다 is_active, deactivated_at, 상태 이력을 사용한다.
- 스키마 변경은 Flyway로 관리한다.

### 8.3 필수 제약조건

- assets의 organization_id와 asset_tag 조합은 unique다.
- 제조번호가 있는 자산은 조직 내 중복을 방지한다.
- 하나의 자산에 종료되지 않은 유효 배정은 하나만 허용한다.
- ended_at은 started_at보다 빠를 수 없다.
- 폐기 완료에는 승인자와 증빙이 필수다.
- 허용되지 않은 상태 전이는 차단한다.
- 금액·수량·날짜의 비정상 값을 차단한다.
- 조직 범위가 다른 객체 연결을 차단한다.
- 감사 로그는 일반 사용자가 수정·삭제할 수 없다.

## 13. 테스트 설계

- 단위: 상태 전이, 권한 계산, 검증, 중복 방지
- Repository: PostgreSQL 제약조건·쿼리·마이그레이션
- 통합: Controller → Service → DB
- API 계약: OpenAPI 응답·오류 형식
- E2E: 로그인·등록·배정·반납·폐기 흐름
- 보안: 권한 우회·조직 범위 침범·세션 만료·레이트리밋
- 부하: 목록·대시보드·보고서

### 필수 시나리오

1. 일반 직원은 다른 부서 자산을 조회할 수 없다.
2. 권한 없는 사용자는 승인할 수 없다.
3. 사용 중인 자산은 중복 배정할 수 없다.
4. 폐기 완료 자산은 다시 배정할 수 없다.
5. 수리 중 자산은 배정 목록에 나오지 않는다.
6. 반복 로그인 실패 시 잠금과 로그가 생성된다.
7. 세션 만료 후 보호 API는 401을 반환한다.
8. 감사 로그에 상태 변경 전·후 값이 남는다.
9. 재시도로 같은 요청이 중복 처리되지 않는다.
10. 헬스체크 실패 시 롤백 절차가 실행된다.

1. 비품관리시스템_전체요구사항및전과정설계.md를 먼저 읽고 현재 단계와 범위를 확인한다.
2. 목표, 사용자, 변경 범위, 성공 기준, 실패 기준을 먼저 정리한다.
3. 요청받지 않은 파일·기능·기술을 임의로 변경하지 않는다.
4. 코드를 작성하기 전에 설계 선택지와 장단점을 제시한다.
5. Controller → DTO → Service → Repository 구조를 유지한다.
6. 인증·인가·조직 범위·감사 로그를 모든 업무 기능에서 검사한다.
7. 자산 상태 변경은 허용된 상태 전이와 트랜잭션 안에서만 처리한다.
8. 비밀번호·토큰·키를 코드나 커밋에 기록하지 않는다.
9. 기능 하나마다 테스트를 추가하고 실행 결과를 보고한다.
10. 실패하면 원인·영향·수정안·재검증 결과를 기록한다.
11. 반복 작업은 상한을 둔다. 같은 오류를 3회 이상 반복하지 않는다.
12. 실제 파일·테스트·실행 결과 없이 완료했다고 주장하지 않는다.
~~~

README와 상태 문서만 만들고 코드는 변경하지 말라.
~~~

### 14.3 2단계: 요구사항·기능 설계

~~~text
비품관리시스템 요구사항을 기능 단위로 분해하라.
각 기능에 사용자, 사전조건, 입력 검증, 정상 흐름, 예외 흐름, 권한, 데이터 변경, 감사 이벤트, 완료 기준, 테스트를 작성하라.
P0 로그인·조직·자산 원장·조회·배정·반납·감사를 먼저 정의하라.
이 단계에서는 코드를 작성하지 말라.
~~~

### 14.4 3단계: PostgreSQL 설계

~~~text
PostgreSQL ERD와 Flyway 마이그레이션 설계를 작성하라.
조직·사용자·역할·자산·배정·상태 이력·구매·검수·수리·폐기·실사·감사·Outbox를 포함하라.
PK/FK, unique, check, not null, index, 조직 격리, 상태 전이를 설명하라.
설계 승인 전에는 SQL 파일을 생성하지 말라.
~~~

### 14.5 4단계: 로그인·권한

~~~text
로그인·로그아웃·현재 사용자·세션 만료·역할·권한·조직 범위를 구현하라.
일반 직원, 부서장, 자산관리자, 감사자, 시스템관리자의 접근 차이를 테스트하라.
다른 조직의 자산 조회가 API 직접 호출로도 차단되는지 검증하라.
~~~

### 14.6 5단계: 자산 원장

~~~text
자산 유형·모델·위치 기준정보부터 구현하고, 자산 등록·수정·상세·검색·필터·페이지네이션을 순서대로 구현하라.
상태 전이는 단일 Service를 통해서만 처리하라.
모든 변경에 이력과 감사 로그를 남기고 테스트를 통과시켜라.
~~~

### 14.7 6단계: 업무 흐름

~~~text
배정 → 이동 → 반납 → 검수 → 수리 → 폐기 → 실사 순서로 한 기능씩 구현하라.
각 기능은 요구사항 확인 → 상태도 → API → DB → Service → 권한 → 감사 → 단위 테스트 → 통합 테스트 → 결과 보고 순서로 진행하라.
한 기능이 완료되지 않으면 다음 기능으로 이동하지 말라.
~~~

### 14.8 7단계: 화면·UI/UX

~~~text
브랜드 아이덴티티 → 제품 성격 → 디자인 유형 → 색상 → 그래픽/폰트 → 레이아웃/간격 → 컴포넌트 → 반복 순서로 디자인 시스템을 확정하라.
컨셉아트 → HTML 목업 → 브라우저 프리뷰 → 사용성 수정 → API 연결 순서로 화면을 구현하라.
로그인, 대시보드, 자산 목록·상세·등록, 배정·반납, 요청함, 실사, 수리, 보고서, 관리자 화면을 포함하라.
~~~

### 14.9 8단계: 테스트·배포·운영

~~~text
정적 검사 → 단위 테스트 → DB 테스트 → 통합 API 테스트 → 프론트 테스트 → E2E → Artifact → staging → 헬스체크 → production 승인 → 롤백 검증 순서로 진행하라.
각 실패 원인과 재검증 결과를 상태 문서에 기록하라.
~~~

## 15. Definition of Done

- 요구사항 ID와 사용자·권한·조직 범위가 있다.
- 정상·예외 흐름이 문서화되어 있다.
- DB 마이그레이션과 API 계약이 있다.
- UI의 성공·로딩·빈 상태·오류 상태가 처리된다.
- Service가 업무 규칙과 상태 전이를 검증한다.
- 감사 로그가 남는다.
- 단위·통합·보안 테스트가 통과한다.
- 변경 파일·실행 명령·검증 결과가 남는다.
- 운영 시 로그·헬스체크·롤백 방법이 있다.

## 17. 미결정 사항

- 단일 회사인지 다법인·다테넌트인지
- SSO/OIDC 제공자와 로컬 로그인 허용 여부
- 실제 승인 단계와 승인자 지정
- 자산번호 규칙과 기존 엑셀 이관 범위
- 감가상각·회계 연동 책임 시스템
- 파일 저장소와 보존기간
- 개인정보·감사 로그 보존기간
- 운영 PostgreSQL 위치와 RPO/RTO
- 알림 채널과 실패 처리
- 모바일 QR 스캔의 1차 제공 여부

결정 전에는 질문·선택지·영향·추천·결정자·상태를 결정로그에 남긴다.
