## 구현

- JPEG·PNG·PDF, 최대 5 MiB, MIME·매직바이트 이중 검증
- 원본명과 분리된 조직/연월/무작위 저장 키, SHA-256, 경로 탈출 방지
- MANAGER/ADMIN 업로드·비활성화, 조직 내 USER 다운로드, Service 재검사
- 업로드·다운로드·비활성화 감사, 삭제 대신 DB·바이너리 보존
- `file_records` 크기·상태·드라이버·행위자와 `asset_files` 유형 제약, FK/부분 인덱스
- 기존 frontend/backend/database 3서비스 유지, backend `file-data` named volume
- 자산 상세 증빙 UI, 별도 HTML mock, 페이지별 자산 상세 컨셉 이미지 갱신
- 운영 외부 저장소가 없으면 production 설정·배포 사전검사에서 중단

## 데이터 흐름

`Browser → Endpoint → Controller → File Service → LocalFileStore + File Repository → PostgreSQL → Repository → Service → Controller → JSON/Download → Browser`

신규 바이너리 저장 후 메타데이터·자산 관계·감사를 짧은 DB 트랜잭션으로 처리한다. DB 실패 시 이번 요청의 신규 파일만 정리하며 비활성화에서는 물리 파일을 삭제하지 않는다.

## 실패와 수정

1. 최초 통합 실행에서 PostgreSQL BIGINT 크기가 JSON 문자열로 반환되어 숫자 계약과 불일치했다. Controller 응답에서 안전하게 Number로 변환하고 전체 12/12를 재검증했다.
2. 모바일에서 기존 `experience.css`의 900px grid 규칙이 기본 720px 규칙보다 늦게 적용돼 671px 넘침이 발생했다. 720px 명시 규칙과 캐시 버전을 갱신해 body 375px로 재검증했다.
3. 최초 frontend 이미지가 신규 `evidence.css`를 복사하지 않았다. Dockerfile COPY 목록을 수정하고 재빌드했다.
