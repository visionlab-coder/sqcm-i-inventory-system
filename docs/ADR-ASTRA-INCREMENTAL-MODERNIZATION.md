# ADR: Astra 감사 후 점진적 고도화

상태: 로컬 기술 결정. 운영 배포·migration·외부 비용 승인이 아니다.
기준: 2026-09-07, HEAD 25ddb5698683c44529a67cdd941aadd1fbfc71e7.
근거: [감사 보고서 166](phase-reports/166_Astra_Product_Audit.md), 계약 108.

## 문제와 대안

| 대안 | 장점 | 위험 / 실제 근거 | 결정 |
|---|---|---|---|
| 현 구조에서 기능 추가만 계속 | 변경 적음 | 배포 내용 불일치와 인증 준비 경쟁 상태를 남김 | 제외 |
| 기존 3계층 유지 + 경계별 점진 보완 | 검증된 API·DB·직원 흐름 보존, 작은 회귀/복구 단위 | 실행기와 실제 배포 증거 연결 필요 | 채택 |
| SPA·Backend 전면 교체 | 새 구조 선택 가능 | 현재 결함이 구조 전체 교체 없이는 해결 불가하다는 증거 없음; 인증·데이터·화면 회귀와 이전 비용 증가 | 제외 |

## 유지할 계약

Nginx 정적 SPA → Express Service → PostgreSQL 16, frontend/backend/database 3서비스 유지. 기존 API URL·RBAC·조직/부서 범위·DB 제약·감사·outbox·멱등성 보존. 기존 migration 수정·데이터 삭제 없음. 오프라인 계정별 저장소와 미동기화 자료 보존.

## 실행 순서와 수용조건

1. R2: logout 후 새 CSRF 준비 전 재로그인 시도 경계를 실제 UI 반례로 확인하고, 재현되면 폼 준비 상태를 명시한다. 시험 대기만 늘려 제품 결함을 감추지 않는다. 서버 인가를 완화하지 않는다.
2. R3: 기존 Excel 이전·현장 실사·생애주기·비용 설명에서 승인 업무의 실제 소비 경로와 계산 근거를 검증한다. 새 기능 수가 아닌 데이터 손실/중복 방지·원인 설명·추적 가능성으로 평가한다. 실제 직원 시간 절감은 UAT 전 주장하지 않는다.
3. R4: 정확한 Git SHA로 후보를 만들고 파일 manifest를 이미지 내부와 대조한다. runtime writable-layer를 정상 릴리스로 간주하지 않는다. 운영 화면 수정은 읽기 대조·보존 후 호환성을 판단한다.
4. R5: 현재 화면 수정 보존, 데이터 백업/복원, 호환 rollback, 대상·변경창 승인과 green 후보 증거가 있어야 배포한다. 기존 이미지 tag만 재배포하지 않는다.

## 회귀·복구

로컬 focused → 실제 격리 DB/HTTP → Chrome 흐름 순으로 검증하고 해당 SHA로 체크포인트한다. JS 수정은 이전 소스/검증된 후보로 복구 가능하나 운영 writable-layer와 데이터 복구는 별도 준비한다. 기존 사용자 dirty는 제외한다. R2~R5 필수 증거가 없으면 완료하지 않는다.

## 제외·미결정

운영 P7 7/8, C5 G4 공급자 5항목, 실제 직원 UAT는 별도 Gate다. public 유지 승인을 private 전환으로 대체하지 않는다. 운영 파일 변경 주체·시각 및 실제 도입 효과는 미확정이다. 변경창·자격증명을 만들어내지 않는다.
